# FlowMQ 上层 MDP 与分布式能力建设方案

设计基线：2026-11-17。单机 RPC 已有 [Client、Broker 和 Worker SDK](../mdp/include/flowmq_mdp.h)，持久单向投递已有 [SQLite 存储接口](../delivery/include/flowmq_delivery.h)。分布式阶段仍为规划。实现范围与调用示例见下文。

目标是在 FlowMQ 上构建服务寻址、Worker 调度和异步请求响应，再通过独立控制面增加主备、多活和服务分片。实施顺序为：FlowMQ 通用能力补强、单机 MDP、分布式授权与迁移。JSON-RPC 作为应用适配层接入。

本方案采用 MDP 的服务注册、空闲调度和会话管理模型，使用 FlowMQ 自有 FMQ 协议承载应用消息。按项目要求不设计旧协议兼容、自动降级或备用实现路径。

## 1 目标和可靠性边界

交付目标包括：

- 有界的 Client、Broker、Worker 通信与执行链路。
- 明确的请求关联、派发、完成、超时和重试语义。
- 控制面与数据面独立的线程、端口、队列和资源预算。
- 共用数据面引擎的模式 A 主备、模式 B 多活和模式 C 服务分片。
- 可验证的授权失效、旧实例隔离、迁移和关闭协议。

元数据 Raft 只保证控制状态的共识与恢复。Broker 的请求队列和在途请求保存在内存中，故障后可能丢失。执行后回复丢失属于结果未知；业务侧持久化幂等键、结果记录和 fencing 是相应业务保证的组成部分。

需要跨进程重启交付的单向消息使用第 5.5 节的持久投递契约。调用者收到接纳成功后，即使此时停止所有进程，恢复时也必须能从发送方或目标收件箱找回消息，或从收件箱的持久记录证明消息已被消费。该保证以两端原有存储完好为前提。最终送达还要求两端恢复运行、授权和路由有效、网络恢复且目标有可用容量。

FlowMQ 的发送接纳、传输完成、对端接收、业务执行和结果送达是不同事件。不得将其中任何一个事件替代另一个，参见 [socket 发送与接收契约](../flowmq/include/flowmq_socket.h)。

微秒级延迟和吞吐量属于后续测量目标。单线程、无锁或使用 MDP 都不能直接证明性能结果。

## 2 当前能力与缺口

以下为设计基线时的实现事实；新增能力与验收要求从第 4 节开始定义。

| 能力 | 当前事实 | 对上层的影响 |
| --- | --- | --- |
| 异步路由与 multipart | 已提供 ROUTER、DEALER、SNDMORE 和 RCVMORE，见 [socket API](../flowmq/include/flowmq_socket.h) | 可承载服务请求、命令和多段 payload |
| wire 与 transport | 使用 FMQ/6；TCP、TLS、IPC、WS/WSS、KCP 能力不同，见 [架构能力矩阵](ARCHITECTURE.md#传输能力) | socket 风格相同不代表与 libzmq 的 ZMTP 网络互通；上层不能扩大 transport 能力 |
| peer 与 endpoint 容量 | 普通 socket 默认 4 个 peer，可在 bind/connect 前配置；peer pool 的配额不超过 socket 预算 | 出站 [destination](../flowmq/include/flowmq_destination.h) 候选和本地主动连接的 endpoint 槽位仍为 4 |
| 发布目标集合 | [runtime](../flowmq/src/runtime/flowmq_socket.c) 在 peer 槽位记录首段订阅匹配的 generation | 槽位复用时清空快照，迟到的尾段无法进入替代连接 |
| HWM | 消息上限 1024，字节上限 64 MiB，见 [option 定义](../flowmq/src/runtime/flowmq_socket_option.h) | 配置不能直接照搬 ZMQ 的 HWM 数值；应用层还需要独立预算 |
| owner | [owner API](../flowmq/include/flowmq_owner.h) 提供调用者驱动的共享等待；socket 容量默认 8、上限 64 | owner 不创建后台线程，socket 仍归固定调用线程 |
| owner listener 与唤醒 | 公开 owner socket 的 bind 返回 ENOTSUP；owner poll 未提供跨线程应用命令唤醒契约 | 普通 socket 可先验证单机流程；共享等待部署需要补齐公开监听和唤醒能力 |
| payload 生命周期 | 接收 slice 转移所有权；成功出队即推进 credit；持有 slice 不延迟归还 credit，见 [接收契约](../flowmq/include/flowmq_socket.h) | MDP 必须限制已出队但仍保留的内存，且在关闭 socket 前释放接收 slice |
| 连接选择 | [destination API](../flowmq/include/flowmq_destination.h) 做连接接纳选择 | 可复用连接选择能力，但服务授权、逐请求调度和应用重试仍归上层 |
| 应用 codec | [FES/1](../flowmq/include/flowmq_esb.h) 已定义应用消息编码 | codec 不提供 MDP 服务注册、执行槽位或集群控制状态 |

当前普通监听器满容量时会暂停新 peer 接纳并继续推进已有 peer，相关正式用例位于 [progress 测试](../flowmq/tests/runtime/test_flowmq_progress.c)。扩容必须保留这一行为。

## 3 模块职责与状态所有者

```text
JSON-RPC adapter                         Raft control plane
        |                                 | committed state
Client SDK ----> MDP Broker <---- Routing snapshot
                     |
                 Worker SDK ----> bounded business execution
        |            |            |
        +------ FlowMQ sockets ---+
                         |
                  FMQ / CNet / transport
```

| 模块 | 拥有的状态 | 边界 |
| --- | --- | --- |
| FMQ Protocol | 帧字段、长度校验、packet 分片重组规则 | 不解释 service、JSON-RPC、授权或重试 |
| Core pattern | socket pairing、方向、路由和 FSM 规则 | 不维护业务服务表或 Worker 容量 |
| socket runtime / owner | peer、连接代际、底层队列、credit、progress 和物理关闭 | 不判断业务执行完成，不重放业务请求 |
| MDP codec | 应用命令、字段和 multipart 形状的编解码规则 | 不连接网络、不调度、不持久化 |
| MDP Broker | 服务索引、Worker 会话、可用槽位、请求队列和派发记录 | 只按当前有效授权接单，不在请求路径调用 Raft |
| Client SDK | pending、请求总时间预算、attempt、路由缓存 | 依据执行确定性和业务策略决定重试 |
| Worker SDK | 进程总并发预算、槽位分配、执行记录和完成队列 | 业务线程不直接访问 socket |
| 控制面 | 集群元数据、授权、迁移阶段、配置提交与恢复 | 不复制业务 payload，不维护本地空闲 Worker 队列 |
| JSON-RPC adapter | 业务 ID、请求校验、notification、batch 和业务错误 | 不改变 FMQ 的连接与接纳语义 |

MDP 与控制面使用独立的上层库或产品模块，经公开 API 依赖 FlowMQ。安装 target、目录和公开头文件在相应阶段实现时确定；不得向当前接口发布未完成的占位 API。下层不反向依赖 MDP、JSON-RPC 或 Raft。

## 4 阶段一 FlowMQ 通用能力补强

### 4.1 有界容量与 peer 扩展

普通 socket 的 I/O owner 在 bind/connect 前设定 peer 预算，默认沿用 4 个槽位。启动后槽位地址保持稳定，满员时由监听器暂停接纳，旧代连接退场后才复用。发布目标使用各槽位的会话 generation，事务选择和 credit 回滚的临时状态归同一 owner。共享 owner 的 backend 有独立的启动预算。出站 endpoint 数与入站 peer 数分别计量。

同一 MDP Broker 可借用多个已绑定的 Worker ROUTER，由调用方一并 poll 并在 Broker 关闭后回收。每个入口保存独立的收包状态。Worker 路由由入口和 identity 共同确定，服务队列、Worker 登记预算、会话租约和在途状态由一个 Broker 统一维护。每个入口的信任策略须与其连接身份来源匹配。原单入口 API 继续可用。

优先级 HIGH。启动配置需要明确 peer、endpoint、connecting、owner socket、消息描述符和保留字节的硬上限。

实施要求：

1. 将固定 peer 存储改为启动时确定的有界存储；启动失败时完整回滚。
2. 同步核对 peer pool、destination、listener、KCP session、fanout 集合和临时数组的容量关系。
3. 路由索引保留 identity 与当前 generation 的对应关系；slot 复用不能继承旧发送、credit 或 multipart 状态。
4. 容量乘法、索引和字节求和使用溢出检查。配置超过可支持范围时明确失败。
5. 达到上限时停止新接纳，已有连接继续 progress；释放 slot 后恢复接纳。
6. 内存成本按实际 peer、队列与 transport 配置计算，避免扩大 peer 数时为每个 peer 隐式预留最大 payload。

容量关系以锁定 SDK 的公开能力为准。后端存在硬上限时，先完成相应 SDK 能力与版本验收，不能通过扩大 FlowMQ 常量绕过后端边界。

验收包括超过 4 个和超过 32 个 peer 的定向路由、PUB/XPUB fanout、满容量接入、slot 复用和关闭。不能只验证 ROUTER 而遗漏共用存储的其他模式。

### 4.2 完整消息对象与发送事务

优先级 HIGH。完整 MDP 消息对象归上层，保存有界 metadata、payload parts、目标会话和发送进度。底层继续提供通用 multipart 接纳能力。

消息对象必须说明各字段采用 copy、move 或 retain 的哪一种语义。入队失败时发送方仍拥有消息；入队成功后由目标队列的 owner 负责终态释放。

发送事务区分组装、等待接纳、已接纳和失败。复制 ROUTER multipart 的非阻塞 final-part HWM 拒绝会取消 route 与 staging；retained multipart 的忙时状态按其独立契约处理，不能共用未经核对的重试步骤，参见 [发送 API](../flowmq/include/flowmq_socket.h)。

Broker 使用非阻塞操作和有界待发送队列。某个 peer 无 credit 时保留该请求的待发送状态，事件循环继续处理其他 peer、完成通知和到期任务。重试不能重复提交已接纳的消息。

首版共享 ROUTER 在选择 identity 前校验整条消息的形状和大小，使用复制型 multipart。非阻塞 final 因 HWM 被拒绝后，从上层拥有的完整消息重新选路。retained final 遇忙会占用 socket 的发送事务，只有在公开接口能将未接纳事务完整撤销或原子拒绝，并通过双 peer 公平性测试后，才可用于此共享发送路径。

协议需要分别限制单 part、完整消息、part 数和 retained range 数。达到 transport 或 retained vector 边界时明确拒绝，不自动切换复制路径。FMQ packet、I/O chunk 和应用 part 保持各自边界；批量处理多个独立请求不改变它们的消息边界。

### 4.3 progress 定时器与应用唤醒

优先级 HIGH。通用 wakeup 仅通知 owner 有工作；应用命令与 payload 由上层有界队列拥有。

优先核对并复用当前 SDK 已发布的 CNet/NativeIO 唤醒能力，在 FlowMQ owner 边界封装生命周期。MDP 不直接操作私有 backend，也不另建网络轮询线程。

Worker 业务完成队列为多生产者、单 I/O 消费者；控制面快照交付使用明确的单生产者通道。所有 socket 收发、登记变更和关闭仍在对应 I/O owner 上执行。

需要定义并验证：

- 生产者先发布命令，再发 wake；消费者读取具备相应的内存可见性。
- wake 可以合并，但从清空队列到进入等待的竞争窗口不能丢失通知。
- 普通数据 readiness、transport progress 和应用 wake 有可区分的返回契约。
- 停止时先禁止新命令，等待 wake 调用者退出，再销毁 wake handle 与 owner。
- 唤醒不授予并发 poll、跨线程 send/recv 或跨线程关闭权限。

上层计算最近的请求 deadline、登记保活、授权到期和维护 deadline，将剩余时间传给 poll；内部网络 deadline 仍由 runtime 缩短等待。每次循环限制网络消息和应用命令的处理量，持续流量不能饿死定时器。

公开 owner listener 需要独立完成接纳、握手 deadline、公平推进和关闭验收。内部 qualification 入口不能直接作为产品 API 使用。传输支持范围必须按正式能力矩阵发布，不因支持一种 listener 就推定 TLS、IPC 或其他 transport 已支持。

### 4.4 上层内存预算与背压

优先级 HIGH。应用预算至少覆盖：

```text
application_budget >= queued_payload
                    + executing_payload
                    + pending_reply_payload
                    + cross_thread_queue_payload
                    + request_and_session_metadata
```

这是预算分项，不是现成容量值。实现还需覆盖 slice 保留大 backing 的实际滞留成本，不能只按借用视图长度估算。

MDP 在接收和调度前预留预算，消息生命周期内转移预算，终态时归还。临时接收和拒绝响应也保留有界空间。队列满时明确拒绝、暂停接收或等待容量，禁止无界扩容和静默丢弃。

已出队消息不再占用 FlowMQ 接收 HWM，因此持续消费到底层队列为空、再无限堆积到应用队列的做法不成立。FMQ 字节 credit、MDP 请求预算和 Worker 执行槽位分别记账。

### 4.5 会话观察与关闭

优先级 HIGH。MDP 登记携带独立的 session 标识，将业务会话与可复用的 routing identity 分开。是否增加通用 peer 事件 API 由实际调用需求决定，不向上层暴露 runtime 内部指针。

重新登记只创建新会话，不自动恢复旧派发记录。旧 session 的回复、完成通知或延迟命令不能释放新 session 的槽位，也不能完成新请求。

关闭时先停止新请求，结算或撤回尚未派发的任务。只要还有执行线程或存储提交可能发布完成通知，I/O owner 就继续消费完成队列并推进 socket。生产者全部退出、通知结算后才能释放接收 slice 并关闭 socket，最后销毁 owner。普通 socket 关闭会取消剩余本地消息，owner socket 通过专用关闭入口回收底层资源。关停期限到达时，RPC 保留已派发请求的结果不确定性，持久投递留下待恢复记录。业务线程仍占用的输入须保留至实际退出。见[现有关闭契约](ARCHITECTURE.md#shutdown)。

## 5 阶段二 单机 MDP

### 5.1 协议范围

采用独立的 FlowMQ 应用协议标识与版本。MDP 0.1 的单服务 Worker 和空闲调度模型可作参考；多槽位、多在途和授权字段属于本项目扩展。[MDP 0.1](https://rfc.zeromq.org/spec/7/) 定义了相应基础模型。

单机阶段由本地不可变配置提供服务分配，经与后续分布式阶段相同的快照消费边界接入；不模拟 Raft 选主或集群租约。接入控制面时替换快照提供者，保留 Broker 调度与应用消息的核心语义。

不复用 `MDPC02` 表示自定义格式；[MDP 0.2 草案](https://rfc.zeromq.org/spec/18/) 已使用该标识，并定义了不同的 REQUEST、PARTIAL、FINAL 格式。具体二进制布局、命令编号和错误编码在 MDP codec 交付时进入正式协议规范。

语义字段至少包括：

| 字段 | 契约 |
| --- | --- |
| command / version | 明确角色、消息类型和严格版本 |
| request_uid | Client 会话标识与单调序号组成的内部请求标识；跨重试保持不变 |
| attempt | 每次新尝试递增，与 request_uid 一起用于回复关联 |
| service | 有长度上限的服务标识 |
| session | Client 或 Worker 的当前登记会话；Broker 重启也生成新 incarnation |
| routing_epoch | 客户端使用的已提交路由版本 |
| assignment_generation | 当前服务分配与授权的代际 |
| remaining_budget_ms | 从原始调用总预算递减；每个节点转换为本地单调 deadline，重试不重置预算 |
| payload_parts | 有界的 opaque payload；保留应用 part 边界 |

时间预算覆盖排队、派发与等待；不直接比较不同机器的单调时钟值。接收端的剩余预算不能精确扣除跨机器传输时间，Client 总 deadline 独立生效；协议不据此承诺业务副作用必然在全局截止时间前结束。错误输入、未知命令、非法状态和越界长度的响应与关闭策略必须由 codec 和状态机共同定义。

请求序号、attempt 和 generation 不得回绕后复用旧关联；耗尽时明确失败或按契约创建新会话。

Client 侧支持调用、结果和派发前拒绝。Worker 侧支持登记及确认、派发、完成、会话保活和断开。Broker 成功发送登记确认后才能从该 Worker 的空闲槽位中派发任务。

**已实现的单机协议 FMR1。** Frontend 使用一个普通 ROUTER，backend 可同时使用多个独立绑定的普通 ROUTER，每个 Client 或 Worker 使用独占的 DEALER。服务由部署提供的准入回调决定。每次调用或登记都校验由 ROUTER 交付的 identity、角色和服务。生产部署须使用可信连接身份，例如为 ROUTER 配置有客户端证书要求的 TLS 身份映射。单机使用固定的本地服务分配，FMR1 没有集群路由 epoch 或授权 generation。Broker incarnation 与 Client、Worker session 由部署分配，重启或替换连接时使用新值。

Client 与 Broker 前端、Worker 与 Broker 后端可分别选择 TCP、WS、普通 KCP 或本机 IPC。每个 ROUTER 绑定一个端点。两端都使用 IPC 时，需要两个独立的命名管道（Windows）或 Unix-domain socket 路径（POSIX）。四种传输共用 FMR1 的登记、派发和回复语义。正式测试覆盖前后端的 16 种组合，超时、重连和槽位回收等故障场景使用 TCP 验证。

每个命令占一个 FMQ DATA part，ROUTER 的路由前缀由 socket 处理。下表给出 55 字节固定头部的偏移。多字节整数采用网络字节序。

| 字节偏移 | 内容 |
| --- | --- |
| 0–4 | ASCII `FMR1` 加 1 字节命令编号 |
| 5–24 | Client session 和请求序号各 8 字节，attempt 为 4 字节 |
| 25–40 | Worker session 与 Broker incarnation 各 8 字节 |
| 41–52 | 槽位、剩余毫秒、带符号状态码各 4 字节。登记命令的槽位字段表示授予的槽位数 |
| 53–54 | 服务名字节数与 payload part 数各 1 字节 |

头部后依次为服务名字节、每个 part 的 4 字节长度、各 part 的内容。服务名为 1–63 个非 NUL 字节。最多 16 个 part，总 payload 最多 4096 字节，允许空 part。命令编号 1–11 依次为 CALL、REGISTER、REGISTERED、HEARTBEAT、DISPATCH、COMPLETE、RESULT、REJECT、UNKNOWN、LEAVE、CANCEL。编解码器校验标识、长度、命令和必需的关联字段。非法输入向 I/O owner 返回 EPROTO，外层多余的 multipart 尾段按有界步数消费。ACK 和持久 DATA 使用第 5.5 节的独立消息格式。

每个 SDK 对象由一个 I/O owner 调用非阻塞 step，并由调用者通过 `flowmq_poll` 推进 socket。轮询上限需覆盖应用可接受的完成通知延迟，并小于保活和请求预算。Worker 的 take/complete 可由业务线程调用，任务和回复都复制到启动时确定的槽位，业务线程无需接触 socket。每个 Worker 实例对应一个业务执行预算。Broker 使用轮转游标选择有空位的同服务 Worker。请求、拒绝响应、每 Client 占用、每服务占用和 Worker 登记均有上限。普通监听器的接入预算由各 socket 在 bind 前配置，Broker 的 Worker 登记额度由所有入口共享。

Client 用 `flowmq_mdp_peek_result` 查看结果与状态码，用 `flowmq_mdp_take_result` 取走结果并释放槽位。收到明确的未派发拒绝后，调用方可以在取走结果前调用 `flowmq_mdp_retry`。它保留原序号、内容和总 deadline，并递增 attempt。取消操作会尝试撤回尚在 Broker 排队的工作。迟到回复按请求标识丢弃。

Broker 关停时先调用 stop 并继续 step，直到 drained 或部署的关停期限。Worker 断线后先 retire，等待业务线程交回已领取的任务，再 close 并以新 session 登记。Worker 接口允许普通业务线程或应用自己的 Actor 执行任务。任务提交完成后，由 I/O owner 在下一轮 step 发送结果。完整的本机 TCP 调用见 [echo 示例](../examples/mdp_echo.c)。

### 5.2 Broker 调度与请求状态

Broker 的服务表、Worker 表和派发表由同一个数据面 owner 修改。可用队列从 Worker 会话和槽位状态派生，不成为第二份容量事实源。

登记和调用准入由应用授权策略校验连接身份与 service 权限。已有 TLS 身份映射可以提供连接身份依据，routing identity 和 peer 自报的服务名本身不授予服务权限。

```text
QUEUED -> DISPATCHED -> REPLY_PENDING -> COMPLETED
   |           |
EXPIRED      UNKNOWN
```

完整派发消息被本地接纳后进入 DISPATCHED；这不证明 Worker 已收到。此后链路失败必须保留执行不确定性。

在每次开始派发前，Broker 重新检查请求 deadline、当前分配、incarnation 和本地授权期限，包括因背压重新选路的尝试。一次尝试由同一 owner 从选择 identity 推进到非阻塞 final 返回，期间不切换分配快照。进入停止派发阶段或授权失效时，尚在上层队列等待的请求结算为明确未派发；已提交的记录按 DISPATCHED 处理。进程暂停可能跨越本地检查和实际发送，外部副作用的提交仍须执行第 6.2 节的 fencing。

- QUEUED：尚未派发，可以撤销、过期或明确拒绝。
- DISPATCHED：占用对应 Worker 会话的槽位，不能因 Client 等待超时就假定槽位已空闲。
- REPLY_PENDING：业务已完成，但回复仍占用有界发送预算。
- COMPLETED：结果发送处理已结束；保留必要的有界关联或去重信息。该状态不等同于 Client 已确认收到。
- UNKNOWN：已派发后无法确认结果；按业务幂等策略决定是否创建新 attempt。

服务等待队列、Client 占用和 Worker 槽位均设硬上限。调度需要防止单一 Client 或服务长期占用整个循环。无 Worker 时按已配置的等待预算排队，到期明确失败。

### 5.3 Worker SDK

一个进程拥有唯一的总执行预算。逻辑槽位分配给 Broker 会话；采用多槽位复用连接时，协议显式携带槽位和 request/attempt 关联，不能直接沿用原版单在途 Worker 契约。

跨 Broker 分配需要保持：各会话已授予的槽位（含空闲与在途）加上脱离会话但仍执行的槽位，不超过进程总容量。断线前仍在执行的任务继续占用进程预算，直到真实完成或确认取消；新登记不能重复释放这部分容量。

首版重连时延迟替代会话的登记，直到原会话脱离后仍在执行的任务全部结束。Worker 在本地回收相应槽位，再按可分配容量登记新会话。其他既有会话继续使用已获授的槽位。代价是一个长任务可以推迟该会话恢复；验收既检查断线期间总并发上限，也检查最后一个旧任务结束后新会话能够派发。

I/O owner 负责登记、收发和保活。业务池只接收拥有型任务，完成后经有界队列交回 I/O owner。结果完成后立即提交回复，不通过延迟回复控制并发。

连接存活由 FMQ 保活观察，MDP 管理业务登记与任务状态。长任务不等同于连接失活。MDP 应用命令本身仍是 DATA，受流控约束；完成和会话管理需要相应的队列预算与调度机会。

### 5.4 Client SDK 与取消

pending 表保存调用者结果句柄、service、request_uid、attempt、总 deadline、当前 Broker/session 和重试策略。回复只匹配当前合法记录，迟到回复按已定义策略释放资源。

第一版取消语义为停止本地等待，并尽可能撤回尚未派发的请求。对已派发请求不承诺停止业务执行。若后续提供远程取消，必须增加“已接受取消”和“任务已停止”的独立确认及资源终态。

重定向只有在 Broker 明确证明请求尚未接纳时才允许安全重发。endpoint 提示必须符合受信 Discovery 的集群身份和传输安全策略；重试次数、跳转次数和总时间均有上限。

### 5.5 跨重启的至少一次投递

首版从生产者的持久发件箱向一个指定的逻辑收件箱投递单向消息。Broker 转发 DATA 和接收回执（ACK），可以在任意一次转发后重启。收件箱身份来自服务配置，独立于 Worker 会话、Broker 地址和进程 incarnation。重新路由必须到达同一份持久接收状态。若新 Worker 只能访问空库，暂停该收件箱的投递并报告不可用。首版恢复范围为进程重启且原存储可用；永久丢盘后的接管需要独立的数据复制方案。

| 事件 | 必须先完成的动作 | 崩溃后的责任 |
| --- | --- | --- |
| 向调用者返回接纳成功 | 发件箱事务提交稳定消息 ID、目标、完整 payload 及 part 边界 | 生产者重启后扫描待投递记录。socket 发送成功仅推进本次传输 |
| 目标签发 ACK | 校验生产者与收件箱权限，以同一事务提交可恢复的完整消息并推进接收序号 | 收件箱自此负责保存消息直至消费提交。重复 DATA 可重新签发 ACK |
| 发件箱回收消息 | 校验回执来自目标收件箱的授权身份，并与当前待投递 ID 匹配，持久提交结算 | 结算提交前崩溃会重发同一 ID。结算后可回收本地 payload |
| 消费者提交处理完成 | 业务处理成功后提交消费位置或删除已处理记录 | 处理后、消费提交前崩溃会再次交付给消费者。要求副作用只发生一次的业务须用同一事务提交业务幂等键与变更，或由外部系统按该键去重 |

**消息标识与去重。** 首版为每个配置的“生产者、收件箱”对建立一条流，用持久的流身份和连续序号标识消息。发件箱在追加事务内分配序号；每条流只发送最早的未确认记录，收到有效 ACK 并提交结算后才推进下一条。收件箱为每条流保存已连续接收的最高序号，与消费位置独立。收到下一序号时原子入箱；收到已提交序号时仅重发对应 ACK；收到跨过缺口的序号时报告协议错误并保留现场。重复包在消费及 payload 回收后仍可识别。流身份与序号禁止复用；流数设硬上限，保留高水位，耗尽时拒绝新流。这一取舍限制单流吞吐，换取每条流固定大小的去重记录。

**重试与失败。** 接纳只覆盖已经提交的一条消息。调用者在提交后、收到成功前断开时，接纳结果未知；提交新的逻辑消息可能产生重复，业务需沿用自己的幂等键。发件箱在 ACK 超时或连接恢复后按原 ID 和原内容重发，重试间隔有上限，每轮扫描有条数和字节预算。调用者停止等待只释放等待句柄。长期断网时待投递记录占用配额；发件箱满则拒绝新的提交，收件箱满则暂停新消息入箱，已提交序号仍可回 ACK。配置、授权、数据损坏或存储提交失败要报告原始错误并停止受影响的操作。提交结果不确定时，恢复后以持久状态判定。恢复需要人工纠正的错误后，才继续原记录。

**存储与线程。** 两端分别限制持久记录数、总字节、单消息大小和待提交内存，并为提交、结算及回收预留空间。存储 owner 通过有界队列接收拥有型消息，提交成功后才向 I/O owner 发布完成通知。恢复按有界批次扫描。存储实现的准入条件是能验证事务原子性和承诺的持久点；普通写调用成功、页面缓存写入或 socket close 均不足以签发接纳成功或 ACK。

## 6 阶段三 分布式控制面

### 6.1 控制状态与 Raft 接入

控制面使用独立端口与线程，不共享业务请求队列。资源预算也单独配置，避免端口隔离后仍被同一无界任务池耗尽。

状态机至少表达以下信息：

| 状态 | 含义 |
| --- | --- |
| metadata_revision | 已应用的控制日志位置，用于恢复与观察 |
| routing_epoch | 拓扑、模式或有效服务分配改变时递增 |
| serving_brokers | Broker 身份、incarnation、公开 endpoint 和服务资格 |
| assignments | 服务的授权集合、generation、迁移阶段；模式 A 包含 active_broker_id |
| lease state | 当前授权续期序号、有效性和撤销依据 |
| migration state | 可恢复的迁移操作标识、目标分配和切换阶段 |

Raft voter 配置由共识库的成员管理协议维护，与 serving_brokers 分开。服务租约到期不直接移除 voter。

引入成熟 Raft 库前完成平台、持久化、线程、TLS、许可证和依赖体积评估。通过独立适配层接入；日志、term/vote、快照、截断、崩溃恢复和安装包依赖都属于接入工作，不能只验收选主。

续约只有提交后才延长授权。Leader 提议条件化的过期或撤销命令，携带 incarnation 与续期序号，状态机确定性应用，避免旧过期命令删除新租约。普通续约不触发路由 epoch 变化和服务重平衡。

### 6.2 授权与 fencing

优先级 HIGH。routing_epoch 只是路由版本，本地快照也可能过期。数据面接单必须同时检查服务分配、Broker incarnation 和授权有效性。

租约协议必须明确单调计时、漂移界、进程暂停、Broker 重启、Leader 更换和恢复后的保守有效期。无法证明授权仍有效时停止新接纳。[Raft 论文](https://raft.github.io/raft.pdf) 对多数派确认和时间型租约的安全前提提供了基础说明；服务授权仍需单独设计。

主备首版为每次续约绑定 Broker incarnation、申请序号和唯一的本地申请起点。设租期为 L，支持的单调时钟速率相对实时时间在 [1−ρ, 1+ρ] 内，且覆盖系统挂起时间。Broker 仅在收到匹配的已提交确认后启用授权，截止点为申请起点加 (1−ρ)L，取整向下。迟到确认、重复通知或重放快照始终使用该截止点，Broker 重启后须重新申请。平台无法验证计时前提时停止租约接单。

切主先提交停止旧代际续约的屏障，状态机拒绝屏障之后到达的旧续约。负责激活的 Leader 观察到屏障已提交后，用自己的单调时钟至少等待 (1+ρ)L，取整向上，再完成 fencing 并提交新授权。屏障之前获准的每次申请都早于等待起点，因此旧持有者最长 L 的实际有效期被完整覆盖。等待中更换 Leader 时，新 Leader 从观察已提交屏障时重新等待整个区间。验收须延迟续约确认超过 L 并在等待中切主，确认旧 Broker 的本地许可不会复活，新授权也不会提前激活。

涉及外部副作用时，新授权激活前安装相应 fencing generation，执行端或业务存储在提交副作用时原子校验。仅在任务开始时校验、仅携带 token 或仅让 Worker 关闭旧连接，都不能隔离暂停后恢复的旧执行。

模式 B 的授权集合允许多个 Broker，同一 generation 表达当前合法集合；不得为每个正常 Broker 递增同一个排他 token，造成多活节点相互撤销。fencing 的实际范围必须与服务、分片或业务资源的写入所有权一致。

### 6.3 快照发布与 Discovery

只发布已应用的不可变快照。控制线程通过有界通道转移快照所有权，数据面只在事件循环边界切换版本；切换前停止使用旧视图，再释放旧对象。不能仅交换裸指针后立即释放旧快照。

快照包括模式、路由 epoch、授权 generation、Broker incarnation、有效 endpoint 和迁移阶段。节点本地的单调授权 deadline 不直接作为跨机器可比较时间发送。

Discovery 明确返回的已提交版本和节点观察状态。Client 不能用低版本覆盖高版本缓存；请求携带比 Broker 更新的版本时，Broker 等待更新或明确拒绝，不按未知版本接单。旧版本是否仍可接纳由当前服务分配和有效授权决定。

请求路径只读本地快照，不同步访问 Raft 或远端 Discovery。

### 6.4 模式与受控迁移

| 模式 | 接纳规则 | 保证边界 |
| --- | --- | --- |
| A 主备 | 已提交配置指定的 active Broker 且授权有效 | 不复制旧主的内存请求队列 |
| B 多活 | 当前有效授权集合中的 Broker | 各自维护本地 Worker 与队列；不提供隐含的全局 FIFO |
| C 服务分片 | 当前服务分配的 Owner 且授权有效 | 服务路由迁移不迁移业务数据或应用会话 |

Raft Leader 负责提交决策，active Broker 由服务授权状态指定。领导权变化与业务 Owner 切换分别完成。

迁移使用可恢复的阶段：准备目标分配和 Worker 容量，停止旧分配的新接纳，drain 在途请求或等待旧授权安全失效，完成必要的 fencing，再提交新分配激活。断网节点不能确认停止时，必须依赖已定义的失效与隔离协议。

模式切换复用上述迁移过程。操作接口返回进度和结果，不承诺修改配置后瞬间无损切换。回滚提交更高 generation 的反向迁移，不降低 epoch 或恢复已撤销的旧授权。

服务映射算法需固定输入规范、hash 版本、种子、排序和权重规则。重平衡结果作为控制命令提交，各节点应用同一结果；算法选择以迁移量和路由规模验收为依据。

## 7 JSON-RPC 适配与错误语义

单机实现提供 `FlowMQ::RPC` 和 `flowmq_rpc.h`。客户端按 service 提交请求，Broker 据此选择 Worker。JSON 解析、方法查找、参数校验和业务执行都在 Worker 侧完成。适配器复用 SaltsBase SDK 的 `Salts::JsonParser`，通过公开 MDP 接口收发，与 HTTP 和具体 socket transport 解耦。业务幂等记录由执行该方法的服务维护。

JSON-RPC id 不替代内部 request_uid。notification 仍需内部完成通知以归还执行槽位，但不能向调用者产生 JSON-RPC response，参见 [JSON-RPC 2.0](https://www.jsonrpc.org/specification)。

首版一个 MDP 请求承载同一服务的一份 JSON-RPC 请求或 batch，由 Worker adapter 处理批内响应。跨服务 batch 的拆分与聚合属于网关适配能力，交付前不宣称支持。业务错误与 MDP 接纳前拒绝采用不同的消息类型，避免将业务返回误判为重定向。

`flowmq_rpc_call` 将单个 UTF-8 文档写入一个 MDP part，沿用 4096 字节预算，同一批次上限为 32 项。Worker 通过 `flowmq_rpc_server_open` 注册不可变的方法表，业务线程调用 `flowmq_rpc_execute` 领取一个槽位、顺序执行批内方法并提交完成。应用可将该入口放在现有 Actor 或业务线程，I/O owner 独立推进心跳和收发。一个调用的结果可超出回复预算，此时 MDP 完成状态为 `SALTS_EMSGSIZE`，已执行方法的副作用仍然有效。

客户端先读取 MDP 终态。对 RESULT 调用 `flowmq_rpc_decode` 校验回复结构并按 JSON ID 关联批内结果；业务错误保存在 JSON 的 `error` 字段。纯通知完成时文档为空。对 UNKNOWN，具有外部副作用的服务可以把业务幂等键、写入和可查询的结果放在同一事务中，供调用方核对最终状态。

| 事件 | 执行确定性 | 处理要求 |
| --- | --- | --- |
| 入队前路由或授权拒绝 | 明确未执行 | 更新受信路由后，在原预算内创建新 attempt |
| 尚未派发时过期或容量拒绝 | 明确未派发 | 返回相应错误，由策略决定是否继续 |
| 本地发送已接纳，连接随后断开 | 可能已执行 | 返回或保留 UNKNOWN，不据此重放非幂等请求 |
| Worker 已完成，回复丢失 | 已执行但调用者不知道结果 | 依赖持久化幂等键与结果查询恢复 |
| 旧 attempt 或旧 session 回复 | 不属于当前等待记录 | 不完成新请求；释放其持有资源 |
| Client 取消等待 | 任务可能继续执行 | 保留真实执行占用，直到完成或确认停止 |

业务幂等策略由服务契约和受信配置确定。Client 声明的标记不能替代业务对可重复执行性的保证。

### 7.1 用户请求的调度与编排

Broker 已按 service 和空闲槽位选择 Worker。请求进入 Worker 后，还有两项决策。**服务方法定义业务步骤**，包括从输入提取哪个业务键、哪些操作冲突、下一步依赖哪些结果、失败或结果未知时如何收束。**Worker 调度已就绪的步骤**，检查顺序、截止时间和容量，决定这一轮推进哪个请求。简单方法只有一个同步步骤，可直接沿用现有入口。公共 RPC 层负责请求身份、等待与完成的交接；订单状态和业务分支保留在服务代码内。

例如，假设订单服务约定同一订单的写入依次生效。先后接纳订单 42 的修改 A、撤销 B，以及订单 73 的修改 C。

| 时刻 | 请求如何推进 |
| --- | --- |
| A 开始 | A 取得订单 42 的写入权，并发查询库存和运费，记录两个子调用后挂起。线程此时可运行其他请求 |
| B、C 到达 | B 按状态所有者的接纳顺序等待订单 42。C 属于订单 73，可以先完成。B 无需反复入队检查 A 是否结束 |
| 运费先回，库存后回 | 两次回复分别归入 A 的对应步骤。方法要求两项均成功，第二项到达后才使提交步骤就绪。重复回复不会再次触发提交 |
| A 提交后 | 记录业务结果，释放订单 42 的写入权，唤醒 B。B 按 A 提交后的订单状态重新校验撤销条件。若 A 的远端写入结果未知，由订单服务决定进入对账状态时 B 哪些操作仍可执行 |

如果库存明确不足，A 可以直接进入业务拒绝，运费回复只用于清理该子调用。如果下一步是已经发出的扣款且结果未知，恢复条件应是查到该笔扣款的结果，不能从“没有收到回复”推导出再次扣款。这两种情况由方法契约决定，调度方只执行已满足条件的步骤。

**调度依据。** 每个已接纳请求有一条有界记录，保存请求身份、截止时间、业务键、当前步骤、已发子调用及其结果。等待队列和就绪队列由记录状态派生。同一请求同时最多有一个就绪项。执行一个步骤前，调度方先检查请求仍有效、前置结果齐备、满足业务顺序且具备所需容量，再记录本次执行身份并交给执行端。返回事件携带请求和步骤身份，只有仍在等待该事件的记录可以推进。一个 batch 沿用一个 MDP 槽位，批内顺序见第 7.2 节。

**排队与公平。** 分区间轮转，分区内的就绪步骤默认按业务键轮转，可按第 7.1.2 节选择 FIFO 或带配额的优先级。一次选中只推进一个步骤，仍可继续的请求重新参与调度。等待子结果、业务键或执行容量的请求退出就绪队列，在对应条件改变时再唤醒。每轮为新接纳、完成事件和到期处理分别留出处理机会。公平范围是可运行步骤；长时间占用执行线程的计算由服务拆步或放入有界计算池。每个热点键的等待数也要设上限，超过限额及时返回过载，以免一个订单占满 Worker。

**顺序的范围。** 只有方法声明冲突的操作才持有同一业务键；整单有序的写操作在等待下游期间继续持有该键。这里的先后以该键的状态所有者接纳请求的顺序为准。多个 Worker 同时服务时，部署须为该键提供稳定的状态所有者，或由共享业务存储通过事务和版本检查维护一致性。现有 Broker 的按服务轮转只提供派发，跨 Worker 的同键 FIFO 需要单独的路由契约。

**执行端。** 服务可在单线程事件循环或串行 Actor 中推进请求记录，也可把独立计算提交给进程内共享的 Salts 线程池。只有请求状态的所有者决定下一步和提交终态。执行端返回成功、错误或子结果事件。线程池非阻塞投递遇满时应保留该步骤、撤销尚未生效的执行预留，待容量恢复后继续；已向下游提交的操作须按其实际结果结算。使用 Actor 或线程池都遵循同一套业务顺序、接纳和完成条件。

#### 7.1.1 微服务派发与按键分区

微服务请求可在同一服务的可用实例间轮转。Kafka 用业务键选择分区，消费者按分区写入顺序读取，同一消费组内一个分区同时分配给一个消费者。FlowMQ 借鉴前者选择独立请求的执行实例，借鉴后者为相互冲突的操作确定顺序。Kafka 的持久日志、已提交 offset 和重放另有存储契约；下面的单 Broker RPC 方案只在当前所有者存活期间保存内存调度状态。[Envoy 上游负载均衡](https://www.envoyproxy.io/docs/envoy/latest/intro/arch_overview/upstream/load_balancing/load_balancers) · [Kafka 分区与顺序](https://kafka.apache.org/intro/) · [Kafka 消费组及 offset](https://kafka.apache.org/41/javadoc/org/apache/kafka/clients/consumer/KafkaConsumer.html)

| 调用契约 | 谁决定去向 | 忙或超时时如何处理 |
| --- | --- | --- |
| 可由任一实例独立完成，如报价计算 | 沿用 Broker 的 service 匹配与空闲槽位轮转，本地 IPC 和远端 TCP Worker 均可成为候选 | 无空槽时按已配置的服务队列和原 deadline 等待；达到接纳上限时拒绝 |
| 必须观察同一实体此前写入，如订单修改、撤销以及要求读到前一次写入的查询 | 服务入口验证输入，按租户和实体生成规范业务键。所有冲突方法共享键空间，映射到固定逻辑分区，由唯一分区所有者接纳并排序 | 键被占用时进入该键的有界 FIFO。所有者忙时保留原归属；排队超时且尚未执行时结束该请求 |

**单 Broker 首版落点。** 为有序服务设置一个受信的调度入口，由一个活动 Worker 会话承接该 service，其他业务 Worker 仍可提供计算或下游服务。顺序从入口校验完成并将请求登记到键队列的时刻开始。配置须保证所有冲突调用都经过这个入口，且同一有序 service 配置 `FLOWMQ_MDP_EXCLUSIVE`。Broker 拒绝第二个活动入口登记，原会话退役后暂停服务，由部署确认隔离后显式恢复。这样 Broker 可以继续转发 opaque payload，现有 FMR1 可承载业务请求。无序服务继续允许多个 Worker 登记。方法由服务契约分类；一个 batch 仍由一个入口按原批内顺序逐项执行，同键成员与其他请求共同遵循键队列的接纳顺序。

**默认分区策略。** 启动时固定分区数 `P`、键的字节编码和稳定哈希，按 `partition = hash(key) % P` 选择逻辑分区。也可按第 7.1.2 节选择一致性哈希环。调度器轮转就绪分区，再按分区的就绪队列策略选择步骤。等待库存回复的订单继续持有本键的写入权，同分区的其他键仍可推进。

**故障与扩容。** 单 Broker 首版采用静态所有权。计划交接先停新接纳，再结清在途工作并移交必要的业务状态，最后启用新所有者；改变分区数也按迁移处理。意外断线时暂停受影响的有序入口。心跳失效不能证明旧 Worker 已停止写入，重新开放前须确认旧执行已停止或由业务存储拒绝旧所有者的写，并核对结果未知的操作。内存 FIFO 无法恢复的已派发 RPC 对调用者保留 UNKNOWN。要求断点续跑的业务需另外持久化操作与完成进度。普通 RPC 的 MDP 回复、业务事务提交、Kafka 的 offset 提交是三个不同的确认点。

#### 7.1.2 可组合的路由与排队策略

服务启动时分别选择**路由策略**与**就绪队列策略**。前者决定请求归属，后者决定同一调度范围内下一个执行机会。方法契约仍负责生成步骤及其依赖。冲突键的队首、前置结果、剩余时间和容量均满足后，步骤才进入就绪集合。策略由受信服务配置选择；共享业务键的多个方法采用相同的键编码、路由和顺序规则。

| 决策 | 策略 | 可观察行为 |
| --- | --- | --- |
| 独立请求选 Worker | 空闲实例轮转 | Broker 从同服务有空槽的实例中轮转，保持现有默认行为 |
| 有键请求选逻辑分区 | 取模哈希或 Ring Hash | 受信入口解析业务键。取模适合分区数固定的部署；Ring Hash 将规范键映射到环上顺时针遇到的首个逻辑分区 |
| 分区内选择就绪步骤 | FIFO | 按步骤进入就绪队列的先后出队；从下游等待中恢复时排到队尾。此顺序约束开始执行的次序，并行步骤可先后完成 |
| 分区内选择就绪步骤 | Priority | 服务按方法及已授权的服务等级确定优先级，各级内部采用 FIFO；采用正整数配额轮转各非空等级，高等级每轮有更多机会，持续就绪的低等级也能推进 |
| 分区内选择就绪步骤 | Round Robin | 对活跃业务键轮转，每次一个键推进一步，仍有就绪工作的键回到轮转队尾。多个租户共享无键服务时也可用受信租户身份作为轮转单元 |

**Ring Hash 的归属。** 环成员使用稳定的逻辑分区 ID，按固定的哈希算法、种子、虚拟节点数及位置冲突排序规则建环。相同配置重建后应得到相同映射。将请求映射到分区后，再由分区的活动所有者处理。所有者忙时请求按原预算在原归属等待；有序写入的归属变更遵循第 7.1.1 节的交接流程。环成员增加时，可通过比较新旧映射确定需要交接的键区间。[Envoy Ring Hash](https://www.envoyproxy.io/docs/envoy/latest/intro/arch_overview/upstream/load_balancing/load_balancers#ring-hash)

**组合示例。** 订单服务可选 Ring Hash 确定订单归属，在每个订单内按写请求接纳顺序排队，再用 Priority 在不同订单的就绪队首之间选择。高优先级撤单仍须等待同一订单此前已接纳的修改；另一个订单的高优先级撤单则可以先获得执行机会。对于普通无状态计算，可选择空闲 Worker 轮转，在同一 Worker 内使用 FIFO。优先级适用于一个调度范围，分区间仍按就绪分区轮转。

**实施边界。** 建环及配额表在启动时校验，重复分区 ID、无效虚拟节点数或优先级配额为零均返回配置错误。默认使用一个逻辑分区，有序请求缺少键时在分类接纳处失败。路由与出队各有一个内部选择入口；请求生命周期、业务键占用及完成提交始终由同一请求记录维护。在途期间沿用已接纳的策略，首版通过停止接纳、排空及重新启动切换配置。Broker 启动时用 `flowmq_mdp_broker_set_policies` 安装路由规则。Worker 通过 `flowmq_rpc_engine_config.schedule` 配置分区、出队及容量，`classify` 回调提供业务键、冲突约束和优先级。[Worker 调度接口](../rpc/include/flowmq_rpc_scheduler.h)

#### 7.1.3 多 Worker 协调调度决策表

先确定一次用户操作需要一个执行者、一组业务步骤，还是指定成员各执行一次。随后选择路由与排队策略。下表给出单 Broker 设计的候选方案及其成立条件，具体实现状态见最后一列。

| 协调场景 | 调度决策 | 状态归属、失败语义与实现边界 |
| --- | --- | --- |
| 同质 Worker 竞争任务 | 有剩余 credit 的同服务 Worker 中，选择 `in_flight / capacity` 最小者，同分轮转。`capacity` 取登记槽位数，`in_flight` 取该会话已派发、尚未结算的占槽数 | Broker 在派发发送接纳后记账，匹配完成或会话退役时结算。Client 超时不能释放仍在用的槽位。满载时走有界等待、拒绝及截止时间；比值只度量占槽。`FLOWMQ_MDP_LEAST_LOAD` 对可用候选按占用比例排序，同分按轮转游标。选择普通轮转时直接扫描现有位图 |
| 本地缓存亲和 | 对可由其他实例正确执行的读请求，按缓存键定位首选 Worker；超过负载阈值时沿环有限探测有 credit 的候选。全部超限时按服务预算等待或拒绝 | 软亲和允许以缓存未命中换取并发。严格有序写继续等待唯一所有者。`FLOWMQ_MDP_CACHE_RING` 在接纳时调用受信 `route_key` 提取业务键哈希，按监听入口序号和 Worker identity 构环，并按每个 Worker 的 `max_load_percent` 筛选可用候选 |
| 串行多步骤加工 | 同进程的短链按步骤直接执行。跨服务链由编排器收到 A 的结果后发起 B，沿用上游关联和剩余预算 | 编排器持有上游回复权。如果将来测量表明逐跳中转值得做协议扩展，还须定义目标服务授权、交接成功点、原槽位释放及中途断线后的唯一回复权。FMR1 的 `0x06` 已用于 `COMPLETE`，当前没有 `FORWARD` 命令 |
| 并行分支与合并（DAG） | 服务定义依赖和汇合条件，编排器在有界预算内启动就绪分支，按子调用 ID 收集结果；预先指定全成功、部分结果或失败终止的条件 | 下游异步 MDP Client 由其 I/O owner 驱动，可复用，单实例容量限制其并发数。服务只对明确未派发或业务可幂等重试的步骤使用剩余预算重试。已派发且结果未知的写入按业务键查询；`flowmq_rpc_engine_fork` 与第 7.2 节的延迟完成配合使用 |
| 防止同资源并发写入 | 单 Broker 使用业务键所有者串行冲突写。共享存储在业务事务内以行锁或版本条件维护提交一致性。分布式阶段可用 Raft 管理分片授权 | 跨所有者切换时，在副作用提交点原子校验 fencing generation，并约束同一代内的冲突写。Raft 租约解决授权归属，版本冲突、陈旧写入和幂等由资源提交契约处理。分布式实现归第 6 节 |
| 全员刷新或全节点检索 | 尽力通知可用 FlowMQ XPUB/SUB。要求全员结果时，协调者先固定本轮目标成员与会话，向该集合扇出，再用带操作 ID、成员 ID、会话的应用回执汇聚。PUSH/PULL 可承载回执，多个 PULL 时须确保回执归入同一份操作记录 | 每个目标最多计一次成功。重复、外来或旧会话回执不能补足人数。到期返回已成功、失败及缺失成员，由调用契约决定是否接受部分结果。`flowmq_mdp_fanout_start` 复制调用方的成员与会话快照，向成员专用 service 发出调用，按 MDP 调用 ID 和实际完成会话汇聚。成员目录与身份绑定由部署提供。[全员回执接口](../mdp/include/flowmq_mdp_fanout.h) |

协议核对：MDP/0.1 定义的 Worker 命令到 `0x05 DISCONNECT`；MDP/0.2 将 `0x06` 用于 `DISCONNECT`。FlowMQ 使用自己的 FMR1 编号。广播的本地发送接纳与目标业务完成也有各自的确认点；FlowMQ retained fanout 的 peer 快照用于发送，不足以证明一次业务操作已在全部目标执行。[MDP/0.1](https://rfc.zeromq.org/spec/7/) · [MDP/0.2](https://rfc.zeromq.org/spec/18/) · [FMR1 命令](../mdp/src/mdp_internal.h) · [FlowMQ socket 契约](../flowmq/include/flowmq_socket.h)

### 7.2 下游 RPC 与延迟完成

现有 `flowmq_rpc_execute` 在 handler 返回时调用 `flowmq_mdp_complete`。延迟完成由 Worker 的 `flowmq_rpc_engine` 驱动。`poll` 返回 START、CHILD、CANCEL 或内部推进事件，`fork` 在客户端 I/O owner 上分组接纳下游调用，`finish` 校验句柄并结算本批成员或最终任务。同步方法继续走现有入口；需要等待下游的方法显式选择延迟完成。两条路径共享请求校验、方法表、批处理规则和回复编码。应用可以按方法迁移，回退时先停止接纳该方法的新调用并结清已有句柄，再恢复同步实现。[同步执行实现](../rpc/src/server.c) · [MDP 槽位实现](../mdp/src/worker.c)

进入等待前，请求状态所有者登记子调用的关联关系和恢复条件。一次步骤结束会释放其执行线程；等待子结果的请求继续占用上游槽位。结果齐备、某项失败和预算到期各自触发方法定义的状态转移；已发分支即使迟到，也要结清本地资源。下表以 Actor 承载服务状态为例。

报价示例在应用层用每个 RPC 票据对应的 CFlow Statechart 实例维护分支状态，多个实例共享一个 SerialExecutor。RPC owner 将子回复解码为可复制的值事件。Statechart 提交汇聚、失败或取消状态后，RPC owner 观察该状态并调用 `flowmq_rpc_engine_finish`。并发回归覆盖子回复乱序、一单取消以及释放槽位后的新请求。[报价示例](../examples/rpc_quote.c)

| 所有者 | 持有的状态与职责 |
| --- | --- |
| Worker RPC 适配层 | 领取前预留有界的延迟请求记录。记录拥有任务身份、所需请求数据、批内位置和回复缓冲。给 Actor 的句柄可以按值入邮箱，校验 Worker 会话、槽位和本次请求身份；重复或过期完成返回明确的失效状态。解析回调借用的 DOM 在跨 action 使用前须转为有所有者的数据 |
| 业务 Actor | 串行维护业务键、等待的子调用及其结果。终态只提交一次。需要下游结果时交还执行权，收到结果、超时或关闭事件后继续推进 |
| 下游 Client 的 I/O owner | 串行提交调用、推进 socket、取走终态。每个已接纳的子调用预留结果存放位置，直到 Actor 消费或关闭流程接管。邮箱满时结果留在记录里，只合并唤醒；消费方清除唤醒标志时复查待处理记录，避免遗漏最后一次完成 |

**接纳与预算。** 上游在途数受 Worker 槽位数和延迟记录容量共同约束。下游还要独立限制每个请求的并发分支数、共享 Client 在途数和保留字节数。启动一个必须并行的分支组前先预留所需本地容量。预算不足时返回该方法定义的过载错误；已有分支被下游接纳时，要结算其真实结果。下游请求使用上游剩余时间，包含在 Worker 队列及邮箱中的耗时。所有上游槽位都可能被等待中的父请求占满，因此依赖服务需要可独立推进的容量；回调同一组已占满槽位时应在接纳前识别并拒绝这种依赖，或在部署时分配独立 Worker。

**完成与退出。** 适配层对每个句柄只接受一次终态。正常会话中，MDP 接受 `complete` 后由 I/O owner 发送，发送接纳后本地槽位才可复用。上游取消等待、超时或断连时，Actor 停止发起新分支；对已观察到的终止事件，结清或取消本地子调用，保证剩余回调不能再访问上游记录，然后交回任务。远端写入结果未知时保留业务幂等键供查询。旧会话、重复或迟到的结果只释放其自身资源。关闭时先停新接纳，继续推进 I/O 与 Actor 完成事件，最后销毁已无回调引用的 Client、Worker 和业务上下文。上游 Client 单方面放弃等待可能对正在执行的 Worker 不可见，Worker 仍按本地截止时间结算。

截止时间以 Worker 收到派发时的本地单调时钟和剩余预算确定。Worker 在接收派发时记录绝对截止时间，`flowmq_mdp_take_task_until` 将其随已领取任务交给执行引擎。Actor 在提交业务结果前复查截止时间，到期后按该方法的超时语义结算。若某个下游写入结果未知而上游连接正常，服务通过 JSON 业务错误告知调用者并返回查询键；前端 MDP 终态仍取决于其自身的投递结果。Actor 异常退出时，Worker 关闭流程接管仍有效的句柄，停止新分支并结算任务，不将旧工作移交给新 Actor 实例重放。

**批请求与通知。** 首版延迟路径沿用批内顺序。当前成员挂起时允许其他上游请求前进，该批次的下一成员等当前成员结束。批内关联使用任务身份和成员位置。全部成员结算后提交一次 MDP 完成，只编码带 JSON ID 的成员；纯通知完成时返回空 body。沿用 32 项和 4096 字节预算。

**实现验收。** 使用正式 RPC 测试驱动下列可观察结果。

| 场景 | 通过条件 |
| --- | --- |
| 两个前端请求，A 等两个乱序子回复，B 先完成 | B 在 A 等待期间收到回复；A 的结果完整且仅提交一次；心跳持续推进 |
| 同一订单的两次有序写与另一订单并发 | 第二次写在第一次结算后开始，另一订单在此期间可完成 |
| 独立计算有两个可用 Worker；有序服务尝试登记第二个入口 | 独立计算可分配给两个 Worker，有序服务始终只有一个活动接纳者 |
| 同服务两个 Worker 分别占用 1/2 和 2/8 槽位 | 选择最小相对负载时下一次派发给 2/8；发送未接纳时两者的占用均不增加 |
| 环上首选 Worker 满载，次选有容量 | 允许缓存未命中的读可选择次选；严格同键写仍受原归属约束 |
| 全员操作有三个目标，两个成功回执来自同一成员，另一个目标中途退出 | 按目标身份去重，成员退出保留在本轮结果中；到期报告缺失或失败，不能宣称全员完成 |
| 相同环配置颠倒成员输入顺序后重建，再加入新分区 | 重建时样本键映射一致；保持原虚拟节点位置时，加入新分区仅移动该分区接管区间内的键 |
| 同一批就绪事件分别使用 FIFO、Priority 和 Round Robin | FIFO 按就绪次序选择；Priority 在高等级持续有工作时仍兑现低等级配额；Round Robin 逐一服务活跃键。三者均保持同键冲突写入的接纳顺序 |
| 同一分区内热点订单等待下游，另一个订单就绪 | 另一个订单在同一分区获得调度；热点订单后续写入保持键内接纳顺序 |
| 有序入口掉线，旧写入结果未知 | 受影响入口停止接纳，新所有者在确认旧写隔离并核对业务状态后才处理冲突写入 |
| 一个请求连续产生就绪步骤，另一个请求中途就绪 | 两者各获得执行机会；热点键达到等待上限时拒绝新增等待，已接纳的独立键仍能推进 |
| 同一子调用重复完成，另一必需分支仍在途 | 提交步骤继续等待，直到所有必需结果齐备；重复完成无法触发第二次业务提交 |
| 线程池或邮箱已满，下游结果同时到达 | I/O 仍可推进；所有已接纳子调用最终可结算，容量恢复后可以接下一单 |
| 回复与截止时间竞争，随后槽位复用或 Worker 重连 | 上游只有一个终态，旧回复无法改变新请求或重复释放容量 |
| 混合 batch 含挂起成员和通知；关闭时还有子调用 | 批内顺序及通知语义一致，退出后无悬挂任务、回调引用或被占用的槽位 |

## 8 实施顺序与验收

下表列出各阶段的交付与验收条件。当前单机 RPC 的实现与公开入口见第 5.1 节。R1 已提供本地持久化接口和独立进程恢复测试，应用负责收发 DATA/ACK 以及安排重发。分布式阶段仍为设计目标。

| 阶段 | 交付范围 | 进入下一阶段的条件 |
| --- | --- | --- |
| F1 容量 | 启动预算、peer 存储、索引与 fanout 集合扩展 | 超过 32 个 peer、满容量、slot 复用及相关模式回归通过 |
| F2 progress | 应用唤醒契约、owner listener 正式入口、deadline 与关闭整合 | 无丢失唤醒；受支持 transport 的公开部署路径通过验收 |
| M1 单机 MDP | codec、Broker、Client/Worker SDK、消息预算与状态机 | 并发调用、长任务、满队列、重连、超时和终态释放通过 |
| R1 持久投递 | 基于 M1 转发的单向 DATA/ACK、持久发件箱与收件箱、消费提交和重启恢复 | 下表中的持久交接故障用例通过，可在同一持久收件箱上恢复；本阶段可独立于 D1 验收 |
| D1 主备 | Raft 持久化、Discovery、授权与 fencing、模式 A | 分区、旧主恢复、时钟边界及执行后丢回复测试通过 |
| D2 多活与分片 | 跨 Broker 槽位分配、服务映射、迁移和模式切换 | 总容量守恒、迁移恢复及三种模式切换测试通过 |
| J1 JSON-RPC 产品接入 | 请求、notification、同服务 batch、业务错误和幂等接入 | 正式适配测试与端到端故障场景通过 |

单机同步 JSON-RPC 随 M1 提供，验证入口为 CTest 标签 `flowmq-rpc`。请求调度与延迟完成的交付条件见第 7.1、7.2 节。D1、D2 的验收另外覆盖跨 Broker 故障恢复和迁移语义。

最小行为验收矩阵：

| 场景 | 必须观察到的结果 |
| --- | --- |
| 4、32 等旧容量边界两侧接入 | 路由正确，无位移溢出、错误 fanout 或旧代际复用 |
| A 的非阻塞 final 持续因 HWM 被拒绝，B 可写 | A 恢复前 B 已收到完整消息，listener、应用命令和定时器继续推进 |
| 业务完成发生在 owner 即将进入等待时 | 无丢失 wake，无需等待下一个维护周期 |
| 业务任务超过保活间隔 | I/O 持续处理保活，执行占用准确 |
| 持续出队并长期保留 payload | 应用预算先达到上限，内存不无界增长 |
| multipart final 接纳失败或连接中断 | 消息终态与所有权确定，重试无重复提交 |
| 相同 identity 快速重连 | 旧回复与旧完成不能修改新会话 |
| Client 超时或取消，Worker 仍执行 | 不提前归还执行槽位或释放输入 |
| 无 Worker 时请求入队，租约到期后 Worker 才登记 | 旧 Broker 零派发；尚能联系的 Client 获得明确未派发的错误 |
| Worker 总容量为 1，唯一任务跨断线继续运行 | 新会话在旧任务结束后才获授该槽位并能接单 |
| 旧主只能访问 Client/Worker，无法访问多数派 | 授权到期停止新接纳，旧副作用受 fencing 约束 |
| 执行已完成但 Broker 在回复前崩溃 | 不自动重放非幂等请求，暴露结果未知 |
| 迁移任一阶段崩溃并恢复 | 从已提交状态继续或执行新的反向迁移 |
| 容量为 1 的完成队列、两个业务任务同时结束并开始关闭 | owner 持续取走完成通知，两个生产者均可退出，引用与槽位全部结算 |
| 发件箱提交前后分别强制终止生产者 | 提交前无成功回执；已经返回成功的消息可在重启后送达，multipart 内容与边界一致 |
| 收件箱提交前终止接收者；提交后丢弃 ACK 并重启 Broker、两端进程 | 首次未提交时由发件箱补送；已提交时仅补 ACK。即使原消息已消费，收件箱也只入箱一次 |
| 发件箱收到 ACK 后、结算提交前终止生产者；重连后注入其他收件箱或旧序号的 ACK | 重发保留原 ID，错误回执无法结算当前消息 |
| 消费者在业务提交后、消费提交前崩溃 | 消息再次交给消费者；对声明幂等的业务核对实际变更次数为一 |
| 两端分别达到配额或提交失败，之后释放容量并恢复；路由暂指向没有原收件箱状态的实例 | 无提前 ACK、无已接纳记录被覆盖；恢复原存储和授权后，积压可在有界内存内排空 |

测试进入现有 TinyTest/CTest 体系，不以源码 marker 或临时日志代替行为验证。构建与正式 target 以实施时的 preset 和 SDK 锁为准。文档阶段不新增生产依赖或修改现有公开 API。

性能验收另行测量繁忙吞吐、连接空闲 CPU、独立到达的唤醒延迟、排队延迟和内存峰值，记录 payload、peer 数、平台、SDK 与后端。正确性测试通过不等于已获得延迟或吞吐保证。

## 9 方案取舍与交付边界

候选方案比较：

| 候选方案 | 评估 |
| --- | --- |
| MDP 和 Raft 直接编入 socket runtime | 初期组合入口较少，但连接、服务、执行与共识状态相互耦合，扩大基础库依赖和回归范围 |
| 独立 MDP 与控制面，经公开 API 组合 FlowMQ | 需要明确消息和快照交付契约，能够独立验证各层状态；采用此方案 |
| 将业务请求与结果也纳入复制日志 | 能增加请求恢复依据，但改变数据面持久化、吞吐和恢复成本；外部副作用仍需幂等或事务协议，按新增可靠性需求另行评估 |

| 选择 | 原因与代价 |
| --- | --- |
| MDP 位于 FlowMQ 上层 | 保持依赖单向，复用已有消息能力；上层需实现完整调度与业务状态机 |
| FlowMQ 只增加通用容量、progress 和生命周期能力 | 其他应用也可复用；公开 API 改动需独立评审和 consumer 回归 |
| 使用独立应用协议版本 | 支持请求关联、槽位和授权字段；Client、Broker、Worker 必须成组发布 |
| Raft 只复制控制状态 | 避免业务请求进入共识热路径；内存队列和在途结果无法靠元数据恢复 |
| 独立评估成熟 Raft 库 | 避免自行实现共识；仍需承担适配、存储、平台和依赖资格验证 |
| 共享不可变消息与快照，显式持有预算 | 保留所有权和容量证据；需要完成跨线程发布、回收与关闭协议 |

旧应用协议不参与混部与版本协商。新网关按独立部署单元交付，启用前完成 Client/Worker 配套发布。停止某种模式或撤销分配时先完成 drain 或隔离；配置回退通过新的已提交变更实施。停用持久投递前先停止接纳，待已接纳记录结算，或保留原存储与恢复入口。跨节点复制收件箱、恢复 RPC 调用结果都需要另行设计数据面持久化。
